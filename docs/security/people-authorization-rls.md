# People authorization and RLS — PEOPLE-02

Status: local implementation, **BLOCKED** pending real PostgreSQL 16 CI and migration-upgrade verification. This is an INFERRED ProjectX contract, not a claim about the SevenRooms implementation.

The reference shows access levels, granular permissions, multi-venue context and suspended users. The actual alternate-role behavior U-002 and FLOW-006 outcomes remain UNKNOWN / REQUIRES_OTHER_ROLE and UNKNOWN, respectively. No role template or reference permission mapping is inferred from those observations.

A server-verified identity is bound before calling `withAuthorizedPeopleTransaction` with a separately credentialed restricted PostgreSQL pool. The transaction checks current capability against enabled User, active Organization Membership, active scoped grant and, for Venue permission, active Venue Access. Role names convey no authority. A known target ID is loaded through RLS before the operation callback. SELF mode requires a matching User target. The transaction sets User, Organization, Venue and access mode using transaction-local settings, then commits or rolls back and releases the client. Callers must validate the requested scope and target server-side and keep operation callbacks trusted, parameterized and limited to the approved permission; arbitrary SQL callbacks or client-supplied identity objects are outside this boundary.

The NOLOGIN `projectx_people_runtime` role owns no schema object and has no BYPASSRLS or DDL privilege. A deployment must use a non-owner login inheriting that role, never a migration-owner connection. Ten People tables have explicit RLS read policies; only Roles, RolePermission and scoped grant tables receive restricted INSERT/UPDATE. No physical DELETE is granted. Venue rows require the exact Venue and Organization; Organization and SELF reads require their respective current grants. The global permission catalog is read-only metadata. The narrow boolean SECURITY DEFINER capability lookup is owned by the migration principal, fixes its search path and rechecks revocation; migration credentials must stay outside runtime. Policies do not use FORCE RLS because ownership is deliberately separated and the owner runs migrations. Any additional tenant table or privileged function requires a separate policy and negative tests before exposure.

These tests cover synthetic identities, cross-Organization and cross-Venue isolation, known foreign IDs, absent or malformed context, disabled users, revoked membership/access/grants, scope moves, SQL privileges, transaction cleanup and both clean and prior-migration upgrades. They have not run against PostgreSQL 16 yet. No request route, OIDC flow, session invalidation, durable audit, production step-up, People API/UI or reference behavior is verified here; grant mutation must undergo the high-risk step-up, anti-self-escalation and audit design before exposure.

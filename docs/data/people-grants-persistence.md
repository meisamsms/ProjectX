# PEOPLE-01B grant persistence boundary

Reference evidence: SCR-025 and SCR-026 show access-level and granular-permission controls and an option to create the same access at other venues. Role (ENT-032) and Permission (ENT-024) are INFERRED FROM REFERENCE UI. No reference grant schema, inheritance, precedence, backend scope encoding or permission algorithm was observed. U-002 remains REQUIRES_OTHER_ROLE / UNKNOWN.

ProjectX implementation concepts: organization-owned `roles`, global stable `permissions`, explicit `role_permissions`, `organization_role_grants`, and `venue_role_grants`. The migration seeds exactly the 22 approved IDs from `docs/security/permission-registry.json`; the database tests compare IDs, scopes, risks and descriptions to that registry. No role template is seeded. A Role name grants no permission. Organization roles may map ORGANIZATION or SELF capabilities; Venue roles may map VENUE capabilities only. SELF capability semantics require object-level self enforcement in PEOPLE-02. A role may be granted explicitly at multiple venues within its owning Organization, without duplicating its definition.

Composite foreign keys preserve Role, Membership and VenueAccess ownership. A trigger locks the Membership or VenueAccess row on grant creation or reactivation and rejects a revoked parent; existing grants remain historical after parent revocation. This persistence gate does not implement runtime authorization: PEOPLE-02 must recheck User, membership, access, grant and object state on every protected operation and handle revocation/session invalidation. Both grant tables have independent `revoked_at`, `updated_at` and integer `version` for conditional atomic updates. Callers must apply version preconditions and increments; the database version check guarantees positive values but does not automatically increment. Durable audit events for grant changes remain a later access audit path and are not verified in PEOPLE-01B.

No RLS or runtime database grants exist yet. These tables must not be exposed to request traffic until PEOPLE-02's restricted role, policies and authorization checks are verified. The migration is forward-only and keeps PEOPLE-01 migration/checksum unchanged.

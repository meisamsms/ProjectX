# Tenant isolation and database context — FOUND-TASK-003

APPROVED PROJECTX DECISION: PostgreSQL shared schema, explicit Organization and Venue keys, RLS plus application authorization (ADR-0003). INFERRED implementation contract below; NEEDS TESTING against isolated PostgreSQL. No claim about the reference application's storage.

## Trusted request to database boundary

Authenticate server session, resolve enabled User, active Organization Membership, explicit active Venue Access for Venue operations, scoped capability and target object ownership **before** establishing database context. Client route/body/header Organization or Venue IDs are selectors only; they never establish authority. An Organization admin's cross-Venue Client history read is a separate capability checked by the application; it never makes Venue Access implicit.

Use one explicit PostgreSQL transaction for each scoped query/command unit. Once server authorization succeeds, set transaction-local custom settings, conceptually `app.user_id`, `app.organization_id`, `app.venue_id` and `app.access_mode` using parameter-bound `set_config(name, value, true)` within that transaction. `app.access_mode` may be `venue`, `organization` or `self`; it is derived server-side from the approved operation, not the browser. `app.venue_id` is absent for true Organization-only work. RLS must treat missing, malformed or empty settings as DENY, never as wildcard. Policy parsing must avoid casting malformed text to UUID in a way that leaks details; choose safe helper functions after threat review. Every connection path (jobs, reporting, imports, support tooling) uses the same authorization bootstrap or an independently reviewed privileged path.

Transaction-local settings revert at COMMIT/ROLLBACK, including when a connection returns to pool. Do not use session-level `SET`, unscoped raw queries or context that spans transactions. Reinitialize scope for each transaction; audit pool reuse by sequential ORG-A/ORG-B checks, failures, nested savepoints and cancellation. No query may run on a pooled runtime connection outside authorized transaction context. Runtime SQL injection would still threaten RLS context by setting custom variables, so parameterization, allowlists, restricted DB privileges and application authorization are mandatory. A custom GUC is not a cryptographic credential. Grant membership/permission refresh and revocation must be checked on the current protected operation, not taken from stale session claims; DB policies may independently check active grants for critical records as an extra defense.

Organization-only operations set validated Organization and user, no Venue; Organization-scoped data is eligible only for matching Organization and a separately allowed capability. Venue operations set both validated Organization and Venue; composite ownership and policy require both. Read models and exports inherit source scopes and field minimization. An authenticated global User/Session path uses `self` and verified User ID, never an absent Organization as broad access. Initial bootstrap of User/Organization/Venue is privileged and auditable with an explicit operator path; no automatic public bypass.

## Invariants and non-bypass roles

All tenant records carry `organization_id NOT NULL`; Venue records also carry `venue_id NOT NULL` and a composite FK consistent with Venue's Organization. Runtime role does not own tables, does not have `BYPASSRLS`, cannot alter policies, and lacks schema DDL. Enable and FORCE ROW LEVEL SECURITY for sensitive tables so ownership cannot bypass accidentally; separate owner/migration role from runtime. Restrict direct use of security-definer functions, trusted context helpers and privileged credentials. Backup/restore and schema migration roles have narrowly approved privileges outside normal request routing, with environment boundaries and audit. See rls-policy-model.md.

Negative checks: wrong Organization, wrong Venue within same Organization, known foreign object ID, forged selector, missing context, malformed context, revoked Venue Access, disabled User, session expiry, org-only mode against Venue rows, cross-Venue Client notes, pool reuse and job/export path. Return indistinguishable 404 for foreign/absent object IDs after permission context is established. Inaccessible context selection returns 403 without confirming a foreign tenant exists. Runtime implementation is NOT yet verified.

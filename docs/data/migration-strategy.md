# Versioned PostgreSQL migration contract — FOUND-TASK-003

Status: INFERRED ProjectX deployment rule under ADR-0003/0006. No production migration or package has been created.

- Store deterministic, reviewable, ordered migration files in the future code repository, named with a monotonic version plus bounded purpose (for example `YYYYMMDDHHMMSS_add_membership_scope`). Exactly one runner coordinates deployment; checksum and applied-version history reject modified already-applied files. Forward-only is default. A reviewed forward fix and restore/rollback plan accompany each change; no manual production schema edits.
- Validate on an empty database and on a snapshot of the previous schema using sanitized data. Run transactional DDL where PostgreSQL allows it; explicitly isolate nontransactional steps (concurrent indexes, long backfills), document resume/cleanup points and test interrupted deployment. Production DDL uses the privileged migration role, never the request runtime identity.
- New tenant tables require Organization/Venue keys, composite ownership constraints, RLS policies for all SQL verbs, FORCE RLS where sensitive, indexes supporting scoped reads, SQL grants and negative isolation tests as one reviewable unit. Policy changes require explicit old/new access-matrix diff and both authorized and denied fixtures. A table lacking policy or context must not be exposed to runtime between steps.
- For large tables, use expand → backfill in bounded, resumable batches → validate constraints → switch reads/writes → contract after compatibility window. Do not impose long blocking locks without an impact estimate. No broad cascade deletion or tenant key relaxation. Destructive drop/rewrite needs explicit review, verified backup and tested restoration path.
- Development seeds and disposable multi-tenant test fixtures must be distinct from production bootstrap. Production bootstrap contains only explicitly authorized initial Organization/Venue/admin grants; no live Client data in development/staging. Restore test data must be sanitized before staging use.
- Managed PostgreSQL backups and point-in-time recovery (where available) must be configured and measured against the **design targets** RPO 1 hour and RTO 4 hours; these are not guarantees. Backups are not verified until successfully restored and checked in an isolated environment. Rehearse recovery around schema upgrades, key rotation and failed migrations; record elapsed restore time and latest recoverable transaction. Backup retention and privacy erasure policy remain UNKNOWN and require owner/legal review.
